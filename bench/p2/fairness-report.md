# 公平调度采样报告：同租户 3 父任务 / 单任务独占 / 抢占（T-P2-09 · design 4.13.8）

- 被测对象：`pkg/harnessloop/orchestrator`（`TenantFairness` / `TenantDispatcher` / `ParentQuota` / `TenantGate`）
- 采样方式：直接驱动公开 API（`Register` / `Attach` / `Tick` / `MarkAccepted` / `AllocRows`），
  每个 tick 后采样一次 `hlp_scheduler_alloc` 的内存行（`AllocRows`），不插桩、不改产品代码
- 默认配额：`max_agents_per_tenant=20`、`max_parallel_per_parent=8`、`estimated_tokens=1024/子任务`
- 记录时间：2026-11-16 · 分支 `feature/p2-t4-test`

## 1. 结论摘要

| 问题 | 结论 | 数据 |
|------|------|------|
| 3 父任务是否被单任务独占 | 否。20 个 slot 分成 **7 / 7 / 6**，任一父任务都 < 16（80% 阈值） | §2 t1 |
| 硬上限是否先于 WFQ 生效 | 是。`ceil(20 × 1/3) = 7`：回填时 b 撞到 7 被跳过、队列继续给 a（t5） | §2 t5 |
| 配额打满后的行为 | 只排队，不抢占。`subtask.cancelled = 0`，拒因可区分（`parent_slot_cap` / `tenant_slots_full`） | §3、§4 |
| 单任务独占是否可能 | 只有"租户里确实只有一个父任务"时才可能（份额 1.0 → 上限 20）。新父任务接入后，超额在跑的 slot **不被回收** | §3 t1→t2 |
| token 上限与 slot 上限的关系 | token 上限会先于 slot 饱和：9/20 slot、3072×3 token，11 个 slot 闲置（双配额语义，非 bug） | §5 |
| Windows / Linux 是否一致 | 是。同一驱动在两平台输出逐行一致（纯内存调度，无平台分支） | §6 |

## 2. 同租户 3 父任务：slot / token 曲线（动态份额 1/3，token 上限未配）

每个父任务入队 12 个子任务（`estimated_tokens=1024`），权重均为 1.0。
`slots` 记 `slots_used/cap`，`tok` 记 `tokens_alloc`，`vt` 记 WFQ 的 `virtual_time`，`q` 记 `queue_depth`。

| tick | 本 tick 启动 | tenant | parent-a slots/tok/vt/q | parent-b | parent-c |
|------|--------------|--------|--------------------------|----------|----------|
| t0 | 0 | 0/20 | 0/7 · 0 · 0.00 · 0 | 0/7 · 0 · 0.00 · 0 | 0/7 · 0 · 0.00 · 0 |
| t1 | **20** | 20/20 | **7/7** · 7168 · 7.00 · 5 | **7/7** · 7168 · 7.00 · 5 | **6/7** · 6144 · 6.00 · 6 |
| t2 | 0 | 20/20 | 7/7 · 7168 · 7.00 · 5 | 7/7 · 7168 · 7.00 · 5 | 6/7 · 6144 · 6.00 · 6 |
| t3 | 0 | 20/20 | 7/7 · 7168 · 7.00 · 5 | 7/7 · 7168 · 7.00 · 5 | 6/7 · 6144 · 6.00 · 6 |
| t4 | 0 | 20/20 | 7/7 · 7168 · 7.00 · 5 | 7/7 · 7168 · 7.00 · 5 | 6/7 · 6144 · 6.00 · 6 |
| t5 | **3** | 20/20 | **6/7** · 6144 · 9.00 · 3 | 7/7 · 7168 · 7.00 · 5 | **7/7** · 7168 · 7.00 · 5 |
| t6 | 0 | 20/20 | 6/7 · 6144 · 9.00 · 3 | 7/7 · 7168 · 7.00 · 5 | 7/7 · 7168 · 7.00 · 5 |

读法：

- **t1 的分配顺序是严格轮转**：`a→b→c→a→b→c…`（虚拟时间同步增长）。20 个 slot 用尽时是 7/7/6：
  第 19、20 个给了 a、b 各自的第 7 个，c 停在 6——20 不能被 3 整除，**c 少的那 1 个是池子先满**，
  不是被限流（`ceil(20/3)=7` 的硬上限此时还没轮到 c 去撞）。
- **硬上限真正生效在 t5**：b 已到 7/7，`canAcquireLocked` 直接把它从候选里剔除，
  队列继续给有余量的 a——**硬上限优先于 WFQ，且被跳过的父任务不会造成队头阻塞**。
- **t1 之后三个 tick 都是 0**：租户池满 20/20，WFQ 也选不出"能拿配额的父任务"，于是走
  `NoteQueued` 记拒因（这轮采样到 `parent_slot_cap=3, tenant_slots_full=2`），而不是让队列整体静默。
- **t5 释放 3 个 slot 后的回填**：c 的 `virtual_time=6` 最小，先补 1 个（6→7/7）；随后 a、b 打平在 7.00，
  按 id 取 a，但 b 已在上限 → 剩余 2 个都给 a（a 4→6，vt 7→9）。这条最能说明"WFQ 决定下一个给谁、
  硬上限决定能不能给"是两层独立决策。
- **token 曲线与 slot 曲线同步**（1024 × slots），因为本场景没设 `tenant_tokens`，token 侧不构成约束；
  受约束的场景见 §5。

## 3. 单任务独占：只有"真的独占一个租户"时才发生，且接入新父任务后不抢占

配置改成 `max_parallel_per_parent=20`，先只挂 `solo`（20 个子任务），再把 `late-b`、`late-c` 接进同一租户。

| tick | 事件 | started | solo slots/cap · tok · vt | late-b | late-c | cancelled |
|------|------|---------|---------------------------|--------|--------|-----------|
| t1 | 仅 solo 在租户内（份额 1.0 → 上限 20） | 20 | **20/20** · 20480 · 20.00 | — | — | 0 |
| t2 | 两个父任务接入（份额 → 1/3，上限 → 7） | 0 | **20/7** · 20480 · 20.00 | 0/7 · 0 | 0/7 · 0 | **0** |
| t3 | solo 完成 8 个（释放 8 个 slot） | 8 | 12/7 · 12288 · 20.00 | 4/7 · 4096 · 4.00 | 4/7 · 4096 · 4.00 | 0 |
| t4 | 无变化 | 0 | 12/7 · 12288 · 20.00 | 4/7 · 4096 · 4.00 | 4/7 · 4096 · 4.00 | 0 |
| t5 | 无变化（租户 20/20 满） | 0 | 12/7 · 12288 · 20.00 | 4/7 · 4096 · 4.00 | 4/7 · 4096 · 4.00 | 0 |

三个要点：

1. **t1 的 20/20 是合法独占**：租户内只有一个父任务时 `share = 1`，`cap = ceil(20×1) = 20`，
   单任务吃满整池正是期望行为，不是 bug。
2. **t2 的 `20/7` 是设计上允许的"超额在跑"**：硬上限只作用于**新申请**，对已在运行的子任务不回收
   （REQ-128 明确禁止抢占）。所以接入新父任务的那一刻，超额部分靠"自然完成"逐步衰减，
   t3 释放 8 个后 solo 从 20 降到 12，仍未降到 7。
3. **衰减窗口 = 最长在跑子任务的时长**。这期间 late-b/late-c 只能拿"租户池剩余量"（t3 的 4+4），
   拒因一律是 `tenant_slots_full`（不是 `parent_slot_cap`，因为它们的 cap 还有余量）。
   这解释了为什么"同租户新父任务的首字节延迟"会受老任务尾部拖累——是设计取舍，不是漏实现。

## 4. 抢占验证：配额打满只排队（tenant 4 / 两父任务）

| tick | 事件 | started | a slots/cap · tok · vt · q | b slots/cap · tok · vt · q | cancelled |
|------|------|---------|----------------------------|----------------------------|-----------|
| t1 | 两父任务各入队 6 个 | 4 | 2/2 · 2048 · 2.00 · 4 | 2/2 · 2048 · 2.00 · 4 | **0** |
| t2 | a 完成 1 个（释放 1 个 slot） | 1 | 2/2 · 2048 · 3.00 · 3 | 2/2 · 2048 · 2.00 · 4 | **0** |

- `ceil(4 × 1/2) = 2`，两方各 2，谁都不能吃满 4。
- 打满后**没有任何 `subtask.cancelled` 事件**：不存在"为了给新任务腾位置而杀掉老任务"的路径。
- t2 释放的 slot 回到了 a（a 的 `virtual_time` 2.00 与 b 打平，按 id 取 a）。
  这是严格 WFQ 的正常结果；如果希望"刚释放的配额优先给别人"，需要额外的 anti-affinity 规则，
  当前设计没有，也不在 T-P2-09 范围内。

## 5. token 上限：会先于 slot 饱和（tenant_tokens=10240，3 父任务）

`tenant_tokens = 10240` → 每个父任务 `tokens_cap = ceil(10240 × 1/3) = 3414`，`slots_cap` 仍是 7。

| tick | 本 tick 启动 | tenant | parent-a slots/tok/cap | parent-b | parent-c |
|------|--------------|--------|------------------------|----------|----------|
| t0 | 0 | 0/20 | 0/7 · 0/3414 | 0/7 · 0/3414 | 0/7 · 0/3414 |
| t1 | **9** | **9/20** | 3/7 · **3072/3414** | 3/7 · 3072/3414 | 3/7 · 3072/3414 |
| t2 | 0 | 9/20 | 3/7 · 3072/3414 | 3/7 · 3072/3414 | 3/7 · 3072/3414 |
| t3 | 0 | 9/20 | 3/7 · 3072/3414 | 3/7 · 3072/3414 | 3/7 · 3072/3414 |
| t4 | **3**（a 完成 3 个） | 9/20 | 3/7 · 3072/3414 · **vt 6.00** | 3/7 · 3072/3414 · vt 3.00 | 3/7 · 3072/3414 · vt 3.00 |
| t5 | 0 | 9/20 | 3/7 · 3072/3414 | 3/7 · 3072/3414 | 3/7 · 3072/3414 |

- **token 先饱和**：第 4 个 1024 会让 `parent.tokens` 变成 4096 > 3414，被 `parent_token_cap` 拒掉。
  结果 20 个 slot 只用了 9 个，**11 个 slot 闲置**。这是"slot 与 token 必须同时获取"的双配额语义：
  宁可空转 slot，也不允许单边超支（否则就是"占着 slot 等 token"的饥饿源头）。
- **`ceil` 造成 342 token 的结构性碎片**：3×1024 = 3072，剩 342 装不下第 4 个 1024，
  预算利用率 3072/3414 ≈ 90%。若 `tenant_tokens` 与 `default_subtask_tokens` 不成整数倍，
  碎片比例会更大。建议（不在本次改动范围）：按 `floor` 分配份额并把余数交给"剩余量最大"的父任务，
  或在租户准入时按子任务粒度取整配置。
- t4 释放的 token 只回给了 a（b、c 仍在 3414 上限），说明 `Release` 的归还路径没有"泄漏给其他父任务"。

## 6. 跨平台一致性

同一驱动在 Windows 本机（go1.22.12 windows/amd64）与 `golang:1.22` 容器内各跑一遍，
S1、S3 的逐 tick 输出完全一致（含 `virtual_time` 两位小数与 `queue_depth`）。
原因很直接：这一层是纯内存记账（`float64` 虚拟时间、`sync.Mutex` 保护的计数器），
没有文件系统、时间或平台分支参与决策；`now()` 只写 `UpdatedAt` 这类观测字段，不进调度判断。

## 7. 复现方式

本次只允许改 `fuzz_escape_test.go` 与两份报告，所以采样驱动是**仓库外的临时模块**（`replace` 指向本 worktree），
不新增测试文件。核心驱动（可原样编译运行）：

```go
cfg := orchestrator.DefaultQuotaConfig()                    // tenant 20 / parent 8
fair := orchestrator.NewTenantFairness(orchestrator.FairnessConfigFromQuota(cfg), nil)
disp := orchestrator.NewTenantDispatcher(fair)
for _, p := range []string{"parent-a", "parent-b", "parent-c"} {
    s := orchestrator.NewScheduler(cfg, emitter)
    _ = s.Enqueue(batch(p, 12))                             // 12 个子任务，estimated_tokens=1024
    _ = disp.Attach(s, 1.0)                                 // 权重 1.0
}
for tick := 1; tick <= 4; tick++ {
    started, _ := disp.Tick(ctx)                            // 一轮 WFQ 准入
    dump(fair, tick, len(started))                          // = AllocRows() + TenantActive()
}
for i := 0; i < 3; i++ {                                    // 释放 3 个 slot 观察回填
    _ = parents[0].MarkAccepted(ctx, parents[0].Running()[0].SubtaskID, "acc")
}
_, _ = disp.Tick(ctx)
```

参数变体：§3 把 `MaxParallelPerParent` 设为 20 并在第一轮 tick 后再 `Attach` 两个父任务；
§4 把 `MaxAgentsPerTenant` 设为 4；§5 把 `Fairness.TenantTokens` 设为 10240。
其余代码不变，说明这几条曲线来自同一套准入逻辑，差异只由配置产生。
